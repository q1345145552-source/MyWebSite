## 一、9 条怎么修的

### A1-① 模型润色时改数字，没人核对 —— **这一条是老板反复抱怨的正主**
`ai-service.ts` `refineAnswerWithModel` → 新增 `enforceDraftNumbers` / `extractNumbers`。

代码先把票数、重量、体积算准（`answerDraft`），最后一步交给 DeepSeek「按客服模板改写」，
**模型返回什么原来就直接发给客户**，中间没有任何一步检查数字有没有被改；
更麻烦的是 `chat()` 末尾写审计日志存的也是改写后的版本，事后查不出来是模型改的。

改法：润色稿里**只要出现一个草稿里没有的数字**（改了、编了、四舍五入了），整段作废、发原始草稿。
少说某个数字是允许的（那只是说得简略，不会让客户看到错的数）。
归一化做了三件事，都是为了**别误判**：全角数字转半角、千位分隔符去掉、按数值归一
（`"08"→"8"`、`"0.500"→"0.5"`，这样 `2026-08-28` 改写成 `2026年8月28日` 不算改数字）。
提示词里也加了「数字逐字照抄」，但那只是第一道防线，真正兜底的是这个校验。

**已知盲区（注释里写了）**：模型把数字写成中文（「三百六十七单」）时抓不到。

### A2-② 时间窗按服务器时区算，比北京早 8 小时
`ai-service.ts` `resolveTimeWindow` 整个重写。原来用 `setHours(0,0,0,0)` 取**本地时区**零点，
生产容器没设 TZ → 本地时区就是 UTC → UTC 零点 = 北京早 8 点。
于是北京 0–8 点下的单算进「昨天」、每月 1 号早 8 点前的单算进「上个月」。
**而开发机在中国（UTC+8）本地跑又是对的 —— 这就是「本地测没问题、线上数字不对」的根因。**
现在全程 `getUTC*` / `setUTC*` 手动 +8，不依赖服务器时区。

顺带：运单进度里的「最近更新时间」原来直接把 `2026-08-28T03:28:00.000Z` 发给客户
（UTC + 客户看不懂的格式），改成北京时间的 `YYYY-MM-DD HH:mm`。

### A2-③ 时间筛选用 `updatedAt` 不是 `createdAt`
半年前的货这个月推进过一次状态（到港、清关、派送都会改 `updatedAt`）就被算进「本月发货」。
改成 `createdAt`。口径老板确认过。

### A2-④ 品名匹配会误配
原判断 `name.includes(k) || k.includes(name)`，且**只比对 `order.itemName`**（那存的是第一个货品）。
三个坑：空品名时 `k.includes("")` 恒真 → 那单被算进**每一个**品名的统计；
反向包含让「壳」被算进「手机壳」；「耳机」排第二个货品的订单一张都查不到。
改法：`listOrders` 带上**全部货品行**的品名（只 select `itemName` 一列）；
统计只用**正向包含**；「查不到」时提示相近品名那里**故意保留**双向包含（不参与数字）。

### A2-⑤ 上下文塞整份运单 ID 列表
`evidenceShipmentIds` / `evidenceOrderIds` 两个完整数组进上下文，还 `JSON.stringify(...,null,2)`
每个 id 一行 —— 生产上一个客户 1862 行、上万个字符，模型一个都用不上，每条消息付两次。
改成只给条数；完整 id 照旧在接口返回的 `evidence` 里。知识库改成 8 条 × 500 字封顶。

### A3-⑥ 调 DeepSeek 的 fetch 没超时
`deepseek-client.ts`：Node 的 fetch 默认不设超时，对方卡住要等 300 秒。
加 `AbortController`，默认 **12 秒**（`DEEPSEEK_TIMEOUT_MS` 可改）。
12 秒是倒推的：前端 `apiRequest` 单次 30 秒超时，一条消息串行调两次，12+12 留 6 秒给数据库。
**计时器在响应体读完之后才清** —— 只包住 fetch 挡不住「头发回来了、body 挂住」。

### A3-⑦ 统计明细三个数自相矛盾
客户问「我在途有多少单」，明细里打「总单量 N / 在途中 N / **已完成 0**」——
那个 0 是被筛掉的，不是真的一单没完成；模型润色时很容易写成「您已完成 0 单」。
现在只有「全部运单」才打分项，其他一律只报「符合条件：N 单」。

### A3-⑧ 模型编的单号抢走分支
`trackingNo` 原来是「正则抓的 `??` 模型给的」，模型随便填个非空值就跳过全部统计逻辑。
现在要过两道门：长得像单号（`^[A-Z]{2,}\d{3,}(-\d+)?$`）+ **必须真的在问句里出现过**
（忽略空格横杠再比，所以客户写「TH-CN 0001」时模型帮忙归一化成 THCN0001 仍然认）。

### A1-⑨ 聊天接口没限流、不限长度
`/client/ai/chat` 是**全系统唯一直接花钱**的接口，每条消息固定调两次 DeepSeek，
而它一次限流都没有、消息长度不校验、请求体上限 20MB。
加四道闸（数值老板确认）：**每分钟 10 条 → 每天 200 条 → 单条 500 字 → sessionId 100 字**。
按**账号**计数不按 IP（攻击者是已登录的客户，按 IP 换个代理就绕过）。
三个数值可用环境变量改，填非正整数会退回默认值并打 WARN。

## 二、改的过程中**实测**发现、一起补掉的（不在原清单里）

这几条都是跑测试时撞出来的，性质跟上面同类，不补客户照样会说「数字不对」：

1. **「我这个月一共发了多少货？」原来一个时间筛选都不走** —— 代码只认「本月」不认「这个月」。
   客户问的是本月，系统报的是**开户至今的总数**。而这句话就摆在**推荐问题列表**里。
2. **「最近 3 天异常件有多少？」整句被当成品名** —— 回「未查询到品名『天异常件』相关订单」。
   这句同样是**推荐问题**。原因是「不是品名」的词表有「完成/在途」却独独漏了「异常/退回/取消」。
3. **「我一共有多少单」「我一共发了多少单」被当成品名「我一共有」「我一共发了」。**
   抓品名的正则是 `(任意 1-20 字)(?:有多少|多少单)`，中文没有词边界，前面那截整个被抓进来。
   黑名单堵不住，改成**剥掉开头的人称/副词、结尾的动词**。
   ⚠️ 只剥开头结尾、**不做全局替换** —— 否则「共享单车」会被剥成「享单车」、
   「有机玻璃」会被剥掉「有」。这两个已经写成测试用例锁住了。
4. **认品名时「一个字的品名不认」+「认最长的那个」** —— 前者防客户把品名写成「货」
   （那他问「我这个月发了多少货」就会被当成品名查询）；后者防同时有「壳」和「手机壳」时先撞上「壳」。
5. 给模型的候选品名**先去重再截断**（原来先 `slice(0,40)` 再去重，重复品名会占掉名额）。

另外加了一句**主动说明**：按品名查时若命中的单里夹着别的货，答复里会打
「其中 N 单同时还有别的品名，重量体积按整票统计」——
因为重量体积是整票的，不拆到单个品名（拆就得自己发明一套算法，而方数是要印给客户看的）。

7. 空值不要显示成 0。
