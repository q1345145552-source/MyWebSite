## 二、上线阻断问题

### P1-1 已登录令牌不会因封号或改密码失效

**证据**

- `apps/api/src/modules/auth/token.ts:3-9,30-46`：令牌只包含用户、公司、角色、姓名和过期时间，默认有效期 7 天。
- `apps/api/src/server.ts:41-60`：每次请求只验证签名和过期时间，不重新检查用户状态，也没有 `tokenVersion` 或撤销记录。
- 管理端封号与修改密码只更新数据库用户字段，没有让已经签发的令牌失效。

**影响**

账号被封禁或密码被重置后，之前拿到的令牌仍可继续访问，最长约 7 天。

**修复建议**

给用户增加 `tokenVersion`（或 `sessionVersion`），签发时写入令牌，请求认证时校验当前用户状态与版本；封号、改密码、强制退出时递增版本。补 4 项自动化测试：正常令牌、封号后令牌、改密后令牌、过期令牌。

### P1-2 员工仓库编辑权限被直接放行

**证据**

- `apps/api/src/modules/orders/routes.ts:70-75` 的 `staffCanEditOrderWarehouse()` 固定返回 `true`。
- 该函数用于订单图片上传/删除和运单编辑等写操作。
- `docs/rbac-matrix.md` 与 `docs/domain-dictionary.md` 明确要求员工只能修改获授权仓库，跨仓库只能读取。

**影响**

任一员工都可能修改其他仓库的订单相关数据，现有 `warehouseIds` 权限配置没有真正生效。

**修复建议**

管理员直接通过；员工从当前用户记录解析 `warehouseIds`，只允许目标仓库在授权列表内，未授权返回 403。对所有员工写接口做统一权限中间层和跨仓库回归测试，避免只修这一处调用。

### P1-3 尾程派送写接口存在跨公司修改路径

**证据**

- `apps/api/src/modules/admin-ops/routes.ts:165-266`：创建派送单接收任意 `shipmentIds`，写入前没有用 `companyId = auth.companyId` 校验这些运单。
- 同文件 `270-307`：状态更新直接按 `id` 更新派送记录，也没有公司条件，随后继续修改其关联运单和轨迹。
- 删除接口在 `323-325` 有公司条件，说明创建和状态更新的保护不一致。

**影响**

知道另一公司的运单 ID 或派送记录 ID 时，当前公司的员工/管理员可能修改另一公司的派送状态和运单轨迹。

**当前数据情况**

测试库只读检查中，尾程派送与运单的跨公司不一致记录为 0；这是“代码路径存在，但测试库尚未发现已产生脏数据”。

**修复建议**

事务开始时一次性查询 `id in shipmentIds AND companyId = auth.companyId`，数量必须完全相等；状态更新先按 `id + companyId` 查询，再用查询结果更新。海关、集装箱、结算等所有关联 ID 写入接口同步做同类审计。

### P1-4 部署顺序会让新代码先于数据库迁移上线

**证据**

- `deploy.sh:97-117` 先构建并切换新 API/Web 容器。
- `deploy.sh:119-133` 只用 API 根路径判断就绪；根路径不访问业务表结构。
- `deploy.sh:135-207` 切换后才检查、备份和执行迁移。
- 备份失败时，`deploy.sh:183-186` 明确跳过迁移，同时保留已经上线的新代码。

**影响**

新代码依赖新字段时，根健康检查仍可能通过，但业务接口会持续报错；备份或迁移失败时，这种不兼容状态会被保留。

**修复建议**

采用“构建新镜像 → 检查迁移 → 备份 → 执行迁移 → 启动新容器 → 业务健康检查”的顺序。若必须做到零停机，应先使用向后兼容的 expand/contract 迁移。健康检查至少访问一个会执行 Prisma 查询的只读端点。

## 三、高优先级工程问题

### P1-5 API 有 19 个类型错误，但 CI 和镜像构建都不检查

错误分为 5 组：

1. nullable ID 数组传给 Prisma `in` 条件（2 处）；
2. DeepSeek 错误响应类型不正确（1 处）；
3. 多个路由使用共享错误码中不存在的 `CONFLICT`（6 处）；
4. 订单产品请求/回退类型缺少 `weightKg`、`cargoType`、`domesticTrackingNo`（8 处）；
5. 运单状态流的字符串类型不匹配（2 处）。

`.github/workflows/ci.yml:21-30` 只检查和构建前端；`Dockerfile.api:16-17` 明确注释掉 API 类型检查。因此 19 个错误不会阻止合并或部署。当前 API 由 `tsx` 直接转译仍能运行，但这些错误已经掩盖真实契约不一致。

**修复建议**：先清零 19 个错误，再把 API typecheck、前端 typecheck、前端 build、测试统一加入 CI 和 Docker 构建门禁。

### P1-6 测试库迁移账本与实际可运行状态不一致

Prisma 找到 17 个迁移，其中 10 个显示未执行；但依赖这些字段的 25 个只读接口能够运行。这表明测试库结构与 `_prisma_migrations` 账本不一致，具体形成方式需再查历史操作记录。

**影响**：后续 `prisma migrate deploy` 可能在创建已存在的字段/表时失败，阻断之后所有迁移。

**处理建议**：先逐个比对 10 个迁移 SQL 与测试库实际结构；确认结构已等价的迁移使用 Prisma 官方 resolve 流程补齐账本，缺少的迁移按顺序执行。处理前先做数据库备份。**本次未检查生产库，不能把测试库结论外推到生产。**

## 四、中优先级问题

### P2-1 依赖存在 high 级漏洞

- 根依赖：直接依赖 `xlsx` 有原型污染和 ReDoS，npm 当前未给出自动修复版本。
- Web：5 个 high，包含直接依赖 `next`、`xlsx`，以及 `nanoid`、`postcss`、`sharp`；审计建议把 Next 从 16.1.6 升到 16.3.2。

**建议**：优先升级 Next 并重新构建/回归；评估用维护中的 Excel 解析库替换 `xlsx`，替换前限制导入文件大小、来源和处理时长。

### P2-2 客户订单 API 仍返回金额字段

`apps/api/src/modules/orders/routes.ts:964-968` 的 `/client/orders` 响应仍包含 `receivableAmountCny`、币种、付款状态和付款人等字段。即使当前测试数据可能为空、前端当前未展示，API 契约仍违背“客户端不看价格”的强约束，未来前端或第三方调用可能直接显示。

**建议**：从所有 client 响应 DTO 和共享类型中彻底移除价格/结算字段，并增加响应契约测试；员工和管理员接口按角色保留。

### P2-3 图片上传与读取策略不统一

- 全局 JSON 上限为 20 MB，但部分上传接口只有“非空”检查，没有单接口大小、MIME、文件头校验。
- 订单商品图同时写磁盘和完整 Base64 到数据库，长期会放大数据库和备份体积。
- `apps/api/src/server.ts:144-164` 的 `/images/*` 在认证前公开读取，使用一年公开缓存。拿到图片 URL 的人可直接访问；签收图、收货凭证等可能含敏感信息。

**建议**：统一上传服务，限制解码后大小、允许类型并校验文件头；数据库只存元数据和文件路径；敏感图片改为短期签名 URL 或受认证的下载接口。

### P2-4 PostgreSQL/Redis 默认对所有网卡暴露

`docker-compose.yml:8-14,24-30` 使用 `5433:5432`、`6379:6379`，并提供开发默认密码；Web/API 已正确绑定 `127.0.0.1`，数据库和 Redis 没有同样限制。

**影响**：如果服务器防火墙未拦截，这两个服务可能被外网直接访问。

**建议**：改为 `127.0.0.1:5433:5432`、`127.0.0.1:6379:6379`，生产环境禁止默认密码；如果宿主机无需访问，直接删除 ports，仅保留 Compose 内网。

### P2-5 没有自动化测试

未发现 `*.test.*` / `*.spec.*` 文件，也没有 `test` 脚本。权限隔离、状态推进、金额隐藏、迁移兼容等关键规则只能靠人工验证，回归风险高。

**建议的首批测试顺序**：

1. 公司隔离与仓库权限；
2. 封号/改密后的令牌失效；
3. 客户响应不含柜号和价格；
4. 运单、集装箱、尾程状态流；
5. 多运单派送事务原子性；
6. 数据库迁移从空库和上一版本升级两条路径。
