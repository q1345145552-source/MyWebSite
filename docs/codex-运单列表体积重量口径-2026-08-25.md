# 整改要求：运单列表的「体积 / 重量」改成显示整票总量（2026-08-25）

老板已拍板：**运单列表那两列要显示「这票货一共多少方 / 多少公斤」，不是「父单拆剩多少」。**

（背景：你在 `/staff/shipments/split` 里的 `reconcileFamilyMetric()` 会把父单字段改写成剩余量，
口径本身没问题。但那两列直接取的就是父单字段，全部走完之后生产上会有 900 张单显示 0 方，
员工看不出这票货多大。所以改的是**显示口径**，不是你的算法。）

## 一、口径定义

**运单列表每一行显示的「体积 / 重量」= 这张运单所属订单的合计量。**

依据（都是 2026-08-25 生产库只读实测）：
- 全库 **1038 张订单，没有任何一张挂着 2 张以上的父运单**（`GROUP BY order_id HAVING count(*)>1` 结果为 0）。
  所以「订单合计量」和「父运单整票量」是一一对应的，直接用订单的量即可。
- 订单表的 `volume_m3` / `weight_kg` **只有 8 张是空的**（1038 张里 0.8%），
  空的时候按下面的兜底顺序取。

**取值顺序（三级兜底，缺一不可）：**
1. 订单的 `volumeM3` / `weightKg`（`orders` 表，后端在建单/改单时已按产品行合计写好）
2. 取不到就用「父单 + 它全部子单」的合计
3. 再取不到就用父单自己的字段（保持现状，不要显示 0）

⚠️ **一行都取不到时显示 `—`，不要显示 `0`。** 显示 0 会让人以为真的一方都没有。
这条跟现有的 `totalPackageCountOf()` 注释里那句「一行都没填箱数时不要显示 0」是同一个道理。

## 三、要改的地方（后端 3 处 + 前端 3 处）

### 3.1 后端：三个列表接口都要额外下发订单合计量

**三端接口是各写各的，改一个必须三个都改**（CLAUDE.md 第 8b 条）：

| 接口 | 文件:行 |
|---|---|
| `GET /admin/orders` | `apps/api/src/modules/admin/routes.ts:425` |
| `GET /staff/shipments` | `apps/api/src/modules/shipments/routes.ts:393` |
| `GET /client/shipments/search` | `apps/api/src/modules/shipments/routes.ts:318` |

三个接口目前都是 `volumeM3: decToNumber(r.volumeM3)`（父单自己的值）。

**要求**：
- **保留现有的 `volumeM3` / `weightKg` 字段不动**（别的地方还在用，改了会连累其它页面）
- **新增两个字段** `totalVolumeM3` / `totalWeightKg`，取所属订单的合计量
- `/admin/orders` 已经 `include: { order: ... }`，直接取即可；
  另外两个接口如果没查订单，要把 `order: { select: { volumeM3: true, weightKg: true } }` 加进去

### 3.2 ⚠️⚠️ 最容易翻车的一条：子单行绝对不能显示整票的量

`GET /staff/shipments` 有一个 **`all=1` 模式**（`apps/api/src/modules/shipments/routes.ts:399`
的 `includeChildren`），这个模式会把**子单也一起返回**。

**尾端派送页面用的就是 `all=1`**（`apps/web/src/services/business-api.ts` 的
`fetchLastmileShipments()`）。

如果不加判断，每一个子单行都会显示整票的体积重量 —— 一票货拆成 3 个子单，
尾端派送页面上就会看到 3 行、每行都是整票的量，**比原来错得更离谱**。

**要求**：
- 只有 `parentTrackingNo` 为 null 的行才下发 `totalVolumeM3` / `totalWeightKg`
- **子单行这两个字段直接给 `undefined`**，让前端退回显示子单自己的值
- 这一条请单独写一个测试证明：同一次 `all=1` 请求里，父单行有合计量、子单行没有

## 五、这个系统特有的坑（不知道这些一定会改错）

1. **三端各写各的**，改一个必须三个都改。列表的 `where` 条件和 `take` 默认值也要对齐。
2. **物流轨迹写在子单上**；客户看到的是父单 + 全部子单**合并**后的结果。
3. **柜货关系在 `shipment_container_items`，不是 `shipments.batch_no`。**
4. **后端容器跑在 UTC**，任何「今天」都要按北京时间换算。
5. **海运 22 步 / 陆运 16 步是两套流程，不许串。**
6. **`apps/api` 的 tsc 基线就是 19 个错**，不是你弄的，别去修。
7. **手写 SQL 的列名必须去数据库核**，这个库 `@map` 用得不统一
   （同一张表里 `clientId` 是驼峰、`company_id` 是下划线）。
8. **红线：客户不能看到柜号、不能看到价格。**
   本次改动会动客户端的运单列表，**顺手确认一下别把柜号带出去**。
9. **列表不要静默截断**，也不要把一行都取不到的值显示成 0。
