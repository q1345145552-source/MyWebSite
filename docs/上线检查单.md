# 上线检查单

每次部署照着走一遍。这份清单是 2026-08-28 那次 Next.js 升级踩完坑之后整理的。

## 上线前（本地）

- [ ] `git status` 干净，没有未提交的改动
- [ ] 后端类型检查 0 错：`cd apps/api && npx tsc --noEmit`
- [ ] 前端类型检查 0 错：`cd apps/web && npx tsc --noEmit`
- [ ] 生产构建通过：`cd apps/web && npx next build`
- [ ] 如果这次动了依赖：删掉 `apps/web/.next` 再构建一次
      （旧版本生成的类型文件会让构建报假错，2026-08-28 踩过）

## 上线前（确认生产库）

- [ ] 确认下次部署会跑哪些迁移，**只读**：
      ```
      ssh root@<服务器> 'docker exec xiangtai-postgres psql -U xiangtai -d xiangtai \
        -tAc "SELECT migration_name FROM _prisma_migrations WHERE finished_at IS NOT NULL"'
      ```
      跟 `apps/api/prisma/migrations/` 下的目录名对比，差集就是这次会执行的。
- [ ] 确认没有卡住的迁移（下面这个数必须是 0，否则部署会被拦住）：
      ```
      ... -tAc "SELECT count(*) FROM _prisma_migrations WHERE finished_at IS NULL AND rolled_back_at IS NULL"
      ```
- [ ] 如果这次有新迁移：确认它只增不删（`grep -i "DROP\|ALTER COLUMN" migration.sql`）

## 部署

- [ ] 跑 `./deploy.sh`（这个脚本会先备份、再 `git reset --hard origin/main`、再构建）

## 上线后（必须验，不能只看「部署成功」）

- [ ] 容器都健康：`docker ps | grep mywebsite`
- [ ] **如果这次升了依赖**，确认容器里真的是新版本：
      ```
      docker exec mywebsite-web-1 sh -c 'grep -m1 version node_modules/next/package.json'
      ```
      不一致说明构建上下文里混进了旧依赖（见 CLAUDE.md 教训 37）
- [ ] 打开网站登录一次，看得到运单列表
- [ ] 传一张照片（**接近 10MB 的真实手机照片**，不是小图）——
      这条链路是 nginx → web(3000) → api(3001)，历史上出过 413 事故
- [ ] 点一次导出，用 Excel 打开看数字对不对

## 出问题怎么退

`deploy.sh` 跑完会打印回滚命令，形如：
```
cd <部署目录> && git reset --hard <上一个提交> && docker compose up -d --build
```
