## 三、⛔ 必须先问老板，不许自己决定

### 分柜之后，运单列表上「体积」应该显示什么？

你的 `reconcileFamilyMetric()` 会在分柜时把父单的体积/重量改写成「剩余量」。
口径本身是对的，但拿生产数据跑过之后，有一个**老板会直接看到**的后果：

```
生产现状（2026-08-25 只读实测）：
  已分柜的父单 932 张
    ├─ 900 张：父单件数已经是 0，但体积还挂着整票的量（老数据口径）
    └─  30 张：已经按新口径扣成 0
```

管理员端运单列表那一列「体积」，取的是
`/admin/orders` → `prisma.shipment.findMany({ where: { parentTrackingNo: null } })` 返回的
**父单自己的 `volumeM3`**，不是订单的合计数。

所以：**那 900 张里任何一张再分一次柜，列表上它的体积就会显示 0**。全部走完，列表合计少 1334 方。

数据本身没错（货全在子单上，父单确实一件不剩），但「列表该显示整票的量、还是父单剩下的量」
**是业务口径问题，只有老板能定**。

**要求**：
- **在老板明确答复之前，不要改动列表取数逻辑，也不要写任何"顺手修正历史数据"的脚本**
- 老板选「显示整票的量」→ 改 `/admin/orders` 的取数（父单 + 全部子单合计，或直接取订单总量）
- 老板选「显示剩余量」→ 现状就是对的，什么都不用改

## 四、这个系统特有的坑（不知道这些一定会查错）

1. **物流轨迹写在子单上，不在父单上。** 只查父单必然误报「没有轨迹」。
   客户看到的是**父单 + 全部子单合并**后的结果（`/client/shipments/track` 里 `childShipments` 那段）。
2. **柜子和货的关系在 `shipment_container_items`，不是 `shipments.batch_no`。**
   `batch_no` 是员工手填的可选字段，全库只有极少数填了，拿它 join 等于白查。
3. **后端容器跑在 UTC**（`TZ` 是空的）。任何「今天」的判断都要按北京时间换算，
   直接 `setHours(0,0,0,0)` 得到的是北京时间早上 8 点。
4. **海运和陆运是两套完全不同的流程**（海运 22 步 / 陆运 16 步），
   凡是跟柜子状态、运单状态、物流轨迹、下一站有关的代码，**必须按 `transportMode` 分开取**，不许共用一张表。
5. **`apps/api` 的 `tsc` 基线就是 19 个错误。** 不是你弄的，别去修，只要别让它变多。
6. **手写 SQL 的列名必须去数据库核，不能照 Prisma 字段名猜。**
   这个库的 `@map` 用得不统一 —— 同一张 `client_wallet_accounts` 里，
   `clientId` 是驼峰（没写 `@map`）、`company_id` 和 `updated_at` 是下划线。
   大小写混合的列名在 PostgreSQL 里还必须加双引号。
   ```sql
   SELECT column_name FROM information_schema.columns WHERE table_name='xxx';
   ```
7. **红线：客户不能看到柜号，客户不能看到价格。** 三条缝都要堵：
   字段（`batchNo` / `containerNo`）、正文（轨迹备注里藏着柜号）、免登录接口。
   「前端不显示」不算堵住 —— 数据到了浏览器就是泄漏。
8. **绝不能对生产库跑 `prisma db push`**（会删字段）。迁移必须**只加不删**，
   因为部署时是「先改库、后换代码」，中间那段跑的是旧代码 + 新结构。
